# Yeelight 挂灯主灯手动优先

本文包含 0.6.1 的手动优先修复及 0.6.2 的柔和过渡。安装与升级方式见 [0.6.2 版本说明](RELEASE-0.6.2.md)。

主灯亮度或色温被手动调整后，XH光流停止自动设置这两项，保留手动值；确认切换到另一个输入接口后，才重新按该接口的场景与配置控制主灯。挂灯旋钮、其他控制端等产生的状态变化都视为外部调整。

## 使用行为

- 手动改变亮度或色温中的任意一项，会让出亮度和色温两项控制。
- 同一接口下的配置应用、网络重连、休眠唤醒或应用进程恢复，不解除已保存的手动优先状态。
- 只在显示设备处于唤醒状态、接口已确认且接口 ID 实际改变时恢复自动控制。未知接口、空值及重复回报不算切换；两个接口绑定相同场景仍算切换。
- 手动优先仅暂停亮度与色温的自动写入；主灯开关仍遵循现有场景逻辑，WLED 与挂灯背光继续按原有条件运行。
- 主灯亮度、色温及场景开关使用约 5 秒的柔和过渡。过渡期间保留最新目标，前向照明缓慢适应；WLED 与挂灯背光保持原有跟色响应。
- 更换挂灯地址后，新设备单独建立控制状态。手动优先保存在应用私有数据中，不包含在网页导出的布局 JSON 内；卸载或清除应用数据会清除该状态。

网页的挂灯状态会显示“主灯手动优先 · 切换输入源后恢复”。正常渐变时显示“主灯正在柔和过渡 · 约 5 秒”；正在读取主灯状态或核对疑似手动调整时，会显示暂缓自动调节的原因。若状态尚未保存到磁盘，页面会提示正在重试保存。

## 检测方式

背光颜色仍通过原有 UDP 55444 会话输出。主灯状态由另一条只读 TCP 55443 连接读取：首次取得完整的 `bright`、`ct` 后才允许自动调节，之后监听 `props` 通知，并定期发送 `get_prop(["bright", "ct"])` 回读。只读连接不创建新的 UDP 令牌，也不接管背光会话。

软件自己的亮度指令与色温渐变可能产生滞后的状态通知。出现与预期不同的值时，先暂停主灯自动写入，等待自身指令稳定，再以完整回读核验；确认仍有差异才保存手动优先状态，避免把自身的渐变过程当成手动调节。

## 5 秒柔和过渡

主灯的 `set_bright`、`set_ct_abx` 和场景 `set_power` 使用原生 `smooth, 5000`。亮度与色温目标会在发送前共同登记；游戏模式开启画面亮度联动时，直接采用当前有效画面的主灯亮度，避免先设预设亮度后立刻覆盖。

完整渐变期间不重复追写亮度或色温，也不因重复目标、同源重连或会话刷新而延长当前过渡。画面目标变化只保留最新值，等待前一次约 5 秒渐变及稳定回读完成后，再以同样的柔和方式调整。前向主灯因此采用慢适应，灯带和挂灯背光继续沿原有链路跟色。

自身渐变的中间亮度、色温不会在原先的短稳定期结束后直接判为手动变化。只有请求发起时间晚于渐变及稳定期限的完整回读，才能确认过渡结果。期间若手动修改，软件不会继续追写；稳定回读确认与自动目标不同后，保存手动优先状态并让出两项控制。已保存的手动优先仍只在真实切换输入接口后解除。

TCP 通道断线、数据不完整或未能取得有效回读时，不自动设置主灯亮度或色温。挂灯需要开启局域网控制，并允许显示设备访问上述端口。不同固件的状态回报能力可能不同，不能仅凭背光 UDP 连通推断主灯状态读取可用。

## 验证范围

主机契约测试使用合成状态与本机模拟挂灯，检查自身指令、外部调整、接口切换、持久化及状态协议，不操作真实灯具。实机结果分项记录如下，主机检查不能代替物理操作或长期稳定性验收。
